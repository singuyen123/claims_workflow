# CLAUDE.md

Guidance for AI coding assistants working in this repository.

## What this is

A config-driven workflow engine for insurance claims (AI Challenge 14). The claim lifecycle,
roles, inputs, rules, notifications and loop limits live in `config/workflow.yaml`. The engine
interprets that file; it contains no claim-specific logic.

## Commands

- `npm test` — Vitest (integration tests need PostgreSQL; see `.env.example`)
- `npm run typecheck` / `npm run lint` — must pass before committing
- `npm run cli -- <command>` — CLI (`config validate`, `show`, `run`, `audit`, `verify`, …)
- `npm run scenarios -- --write` — runs the demo scenarios and writes `docs/results/`
- `npm run db:setup` (once), `npm run db:migrate`, `npm run db:seed`

## Architecture rules

- Three layers, dependencies pointing one way: `controllers` → `services` → `repositories`
  (interfaces) ← `repositories/postgres` (implementations); services also use `engine`.
  `src/bootstrap.ts` is the only place that wires implementations into services.
  `tests/unit/architecture.test.ts` enforces the import rules.
  - **Controllers** (`src/controllers/http`, `src/controllers/cli`): parse and validate input
    (zod, headers, CLI args), call exactly one service method, then return, render or map the
    result to an HTTP status or exit code. No business rules, no `AppContext`/pool, no imports
    from `repositories/`, `infra/db` or `pg`.
  - **Services** (`src/services`): all logic. Data access only through repository interfaces;
    transactions through `UnitOfWork.transaction`. Never import `pg`, `infra/db` or
    `repositories/postgres`.
  - **Repositories**: interfaces in `src/repositories/*.ts`, PostgreSQL implementations in
    `src/repositories/postgres/`, the only place with SQL besides migrations.
- `src/engine` is pure: no I/O, no `Date.now()`, no randomness. Time and ids are injected.
- Never add workflow-specific behaviour (state names, transition ids, roles) to TypeScript.
  If a new behaviour is needed, add a generic condition/effect primitive and use it from config.
  Only `tests/` and `src/scenarios/` (scripts that drive the shipped workflow) may name them.
- Every config path (`$claim.x`, `{claim.x}`) must type-check in `src/engine/validate.ts`.
  When adding a primitive, extend the validator and add a test with a broken fixture.
- The engine never reads audit history. Anything a rule needs (counters, participants,
  `state_entered_at`) is kept on the claim snapshot.

## Data conventions

- Data (YAML, DB columns, JSON payloads, audit fields) uses `snake_case`; TypeScript identifiers
  use camelCase.
- Money is an integer number of VND. Timestamps are ISO-8601 UTC strings with millisecond
  precision, generated by the injected clock (never `now()` in SQL for hashed values).
- Migrations in `src/infra/db/migrations` are append-only: never edit an applied file
  (the runner verifies checksums). Add a new numbered file instead.
- Audit tables are append-only (DB triggers). Tests that need a clean slate drop their schema.

## Environment

- Windows dev machine: run git through Git Bash; npm scripts must stay cross-platform
  (no inline `VAR=x cmd`).
